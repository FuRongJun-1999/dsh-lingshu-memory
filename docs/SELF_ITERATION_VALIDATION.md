# 自指迭代与分阶段封版协议（提案）

状态：proposal。本文定义项目维护流程，不修改 core 契约、不授予生产资格，也不构成形式证明。核心语义规则仍以 [core.json](<../spec/core.json>) 及其冻结锁为准。

## 1. 目的与共因风险

本项目使用多智能体工作流维护自身。同一模型、提示、规则、测试或工具可能同时作用于实现与验证，形成共因错误：工作流顺利完成任务，不等于工作流判断正确，更不等于系统生产可用。

因此每个阶段同时是一次受限的架构实验，必须满足：

- 变更范围绑定明确的基线提交、组件集合与需要保护的不变量；
- 实现者不能单独决定自己的候选晋级；
- 实现者生成的测试、摘要或代理评价，不单独构成独立验证；
- 未运行、无法读回或证据冲突的门禁保持 `NOT_RUN` / `unknown`，不得推断为通过。

## 2. 三条版本轴

三种版本状态互不替代，均需在阶段回执中记录：

| 版本轴 | 表达什么 | 约束 |
|---|---|---|
| 规范版本 | `core.json` 的契约语义 | 当前 `0.2.0`；本协议不升级、不改写。 |
| 工程阶段版本 | 一组可审阅的项目变更 | `stage-N` 绑定 PR 与提交；标签只表示范围冻结。 |
| 证据等级 | 实际通过了哪些对象与环境 | 逐项声明，如 `spec-tools=PASS`、`shadow-process-crash=PASS`、`C5=ISOLATED_ACCEPTED`；不得压缩成无范围的“1.0 通过”。 |

在项目仍为设计/参考/隔离实现期间（`runtime_released: false`），不使用含混的 `1.0.0 stable` 标签。工程阶段可用 `v1.0-stage.N-rc.M` 作候选标识；正式稳定标签须由维护者另行裁定发布语义后创建。任何标签都不改变 `core.json` 版本或 `runtime_released`。

## 3. 候选状态机

```text
planned -> implementing -> candidate-frozen -> independently-verified
                                      |                  |
                                      |                  +-> accepted-for-stage
                                      |                  +-> rejected / needs-revision
                                      +-> invalidated (基线、源码、测试、工具或环境变化)
```

- `planned`：范围、基线、组件、风险、退出条件与不适用边界已写入阶段任务单。
- `implementing`：允许变更；期间的测试结果只用于调试，不能签发本阶段结论。
- `candidate-frozen`：候选提交、文件清单、规格锁、测试树与证据输入已固定；此后任一相关改动都使候选失效，需新建候选标识。
- `independently-verified`：按第 4 节完成独立性复验，所有要求项均有可读原始回执。
- `accepted-for-stage`：阶段门通过，可在声明范围内合并或封版。
- `rejected / needs-revision`：存在反例、矛盾、漏项、未运行门禁或独立性不足；退回新候选，旧证据保留但不得覆盖。
- `invalidated`：候选冻结后相关输入变化，既有验证自动失效；不得通过改写旧报告“更新”冻结候选。

阶段接受不自动晋级 `M6`、production/power release gate 或真实迁移。设计/隔离能力可在生产资格未取得时继续建设，但必须列出依赖与未关闭风险。

## 4. 自指验证隔离

每个阶段至少设置两个时间上分离的验证窗口，并至少覆盖一个组件隔离的判据面。

1. **实现窗口**：实现者完成变更并提交摘要，不作最终验收。
2. **冻结窗口**：记录候选提交、工作树/文件清单、依赖、环境、命令、预期与失败处理；冻结后由独立编排者锁定不可变输入。
3. **独立复验窗口**：候选冻结后另起会话或由不同执行主体，重跑选定门禁并读取原始结果，不得只引用实现者结论。
4. **跨组件检查**：对被改组件使用另一个组件、手写预期或外部可观察接口作判据。例如改 shadow 存储时用真实重开实例检查持久投影；改规格生成器时用冻结输入检查产物与反向漂移；改调度编排时用 worker 原始 status/result 而非编排者摘要判定。
5. **延迟复验**：至少一项关键不变量在后续独立时段针对同一候选摘要复验；候选变化则新建证据，不移植旧 PASS。

同一底模、同一上下文、共享同一实现摘要的多个代理只算多个审查视角，不算统计独立。无法取得不同主体或独立执行时，须标记 `independence=limited` 并限制晋级范围。

### 4.1 独立性分级

| 级别 | 含义 | 用途 |
|---|---|---|
| `I0 coupled` | 实现者自测或同上下文复看 | 仅调试，不签发 |
| `I1 fresh-context` | 新会话复跑，但主体/工具/判据仍共享 | 低风险内部检查 |
| `I2 independent-operator` | 不同执行主体按冻结步骤操作并读原始结果 | 一般阶段门 |
| `I3 cross-component` | I2 加不同组件或独立 oracle/手写预期 | 关键不变量默认门槛 |
| `I4 delayed-replication` | I3 加后续时段对同一候选摘要复验 | 持久化/授权/迁移等高风险主张 |

每条关键结论记录：`candidate_sha`、被测组件、验证者身份/角色、是否与实现者相同、会话标识、验证时间窗、执行环境、原始命令与结果位置、预期来源、依赖输入摘要、盲区与偏离项。

## 5. 冻结证据包

每个候选提供可读 manifest，至少包含：

- 阶段 ID、目标、非目标、基线提交、候选提交、精确文件与组件清单；
- 本阶段要保护的不变量及来源；每条正例、负例、故障注入与变异的预期结果；
- 原始命令、工具与 worker 版本、操作系统与解释器版本、起止时间、退出码、测试数/子测试数、失败与跳过计数；
- 独立性账本、覆盖矩阵、未覆盖面、已知共因风险与复验计划；
- 规格、文档、公开内容与隐私门禁读数；若刷新源指纹类报告，须证明重新实跑并读回；
- 对应 PR、提交与远端 CI 回执；生产状态文件与 release gate 摘要。

证据产物只描述实际观察。日志被截断、工具超时、代理无法读取源文件、远端 CI 未运行或状态读取失败，一律保留为 `unknown` / `NOT_RUN`，不得由总结补齐。

## 6. 阶段门与封版

每个阶段以独立 PR 交付，合并或封版前至少满足：

1. 变更范围与冻结基线可复核，无意外夹带；
2. 针对性回归通过，风险相符的故障/变异测试能杀死对应缺陷变体；
3. 由不同主体/新上下文完成 `I3` 复验；高风险阶段安排后续时段 `I4` 复验，或保持候选不晋级；
4. 文档、生成产物、索引与规格锁一致，公开内容与隐私扫描无命中；
5. PR 的 base/head/CI 实时读回，生产验收登记未被隔离结果改写；
6. 复核者已列出发现及范围限制；阻断项清零，非阻断待办有负责阶段。

封版只冻结某候选的源码与适用证据，不是自动合并、自动发布或生产授权。若发布阶段标签，标签必须指向已验收的精确提交，并附同一证据 manifest 摘要。

## 7. 首阶段与后续顺序

本文件即 `stage-0: self-verification protocol` 提案：只定义流程，不更改 `core.json`、release gate 状态或运行时行为。独立复核通过并合并后，后续阶段按风险分开选择：P2 metadata 类型与值域硬化；intent/WAL 与平台故障边界实验；版本冻结工具化；`M6` 授权迁移前置评审。不同阶段不得把验证工具自身的 PASS 当作它正确的自证。

M0–M5 现状与 M6 门槛仍以[路线图](<ROADMAP.md>)、[章程](<CHARTER.md>)、[恢复规范](<RECOVERY.md>)与[核心规格](<../spec/core.json>)为准。C5 的 `ISOLATED_ACCEPTED` 只覆盖其声明的 `framework`、`sandbox_runtime`、`tests`（含 `tests/test_shadow_runtime*.py`）与 context 指纹及隔离合成流程，不覆盖 `shadow_runtime/` 实现文件；它既不能证明 shadow 实现正确，也不构成 production/power 证据。`spec/acceptance.status.json` 与 release gate 仍是生产资格真源，不由此流程自动改写。

## 8. 不适用与限制

本提案不是共识协议、加密签名、形式证明、独立组织审计或抗恶意管理员篡改。复核者可能共享模型、库、工具或策略而产生共同失误；`I3`/`I4` 只降低并暴露部分共因风险，不能消除风险。涉及凭据、真实个人数据、生产迁移、线上部署或破坏性操作，仍需单独授权与专项门禁。
